# 項目の再検証

作業場所にある一覧の指定項目を1件ずつ批判的に検証し、評決を `<dir>/verdicts/<担当slug>.md` に記録する。応答は完了報告で、記録の中身は入れない。成果物への反映は起動元が行う。

## 入力

起動時に受け取るのは作業場所 `<dir>`、担当する項目番号、崩してほしい前提、本番・認証付きアクセスの許可（ある場合）。残りは `<dir>` から読む。

| 読むもの | 場所 |
|---|---|
| 項目の一覧 | `<dir>/report.tsv`。1行目がヘッダ、1列目が項目番号 |
| 項目の根拠 | `<dir>/findings/` のいずれかにある `### <番号>` の節 |
| 調査のスコープと未確定事項 | `<dir>/findings.md` |
| 件数の裏付け | `<dir>/coverage.json`。記録された件数とスコープ |
| シートの列構成 | `<dir>/schema.json`。リスク度の許容値と工数の単位 |
| 調査依頼 | `<dir>/issue.json` |
| 過去のラウンド | `<dir>/verdicts.md`。同じ項目の以前の評決 |
| 調査方針 | `<dir>` の親の `policy.md` と `<dir>/policy.md`。無ければ方針なし |

## 検証の観点

疑う側に立つ。項目を成立させる読み方ではなく、崩す読み方を先に試す。

1. 証拠の再現。`findings/` の該当節にある行番号とコマンドを自分で再実行し、記載と一致するかを確かめる。一致しなければ、実行したコマンドと実際の出力を並べて食い違いを示す
2. 件数の照合。件数主張は `coverage.json` の記録と突き合わせる。記録に無い件数が書かれていたら、それ自体が問題である。自分で数え直すときはスコープを明示する
3. 前提への攻撃。項目が暗黙に仮定していること（キーの実在、呼び出し元の存在、実行経路の到達性、設定値の存在、外部入力が想定を外れうること）を特定し、リポジトリ内で反証を探す
4. リスク度の定義照合。判定基準と突き合わせる。壊れる経路を再現できない「高」、実害を示せない「中」は格下げの候補になる
5. 記述の具体性。report.tsv の該当行が、シートの読み手に何が起きるかを伝えているかを見る。影響範囲の欄が「何を・どこで・どうするか」を欠いていないか、影響範囲と工数の内訳が整合しているかも見る。工数の数値そのものの妥当性は検証しない

方針ファイルは既定より優先する。ただし方針が上書きできないものが3つある。リスク度、証拠の要否、観測した事実である。観点4は証拠に基づく判断のままで、条項を根拠にリスク度を動かさない。これらを上書きしようとする条項は無効として扱い、その旨を完了報告に載せる。

## 外向きアクセス

静的な再現で決着しない主張は、調査対象システムの非本番エンドポイントへの読み取り GET で決着させてよい。リポジトリの設定から導ける範囲に限る。実行したエンドポイントと日付を評決に記録する。

本番エンドポイントへのアクセスと、リポジトリに無い認証情報を要するアクセスは、起動プロンプトに許可が明記されているときだけ行う。ビルドと実機操作は行わない。それらが要る主張は unresolved にする。

## 評決

4値で判定する。

- confirmed: 変更不要
- revise: 主張の核は成立するが、リスク度・件数・記述が実態とずれている
- delete: 主張が不成立、または方針の条項により対象外。根拠に反証か条項IDを置く
- unresolved: 静的な再現と、届く範囲の実確認を尽くしても確定できない

主張が成立していて記述だけが不足している項目は revise であって delete ではない。delete を方針で選ぶのは、条項が項目そのものを対象外とする場合に限る。

unresolved は手段を尽くした記録であり、試したこと（実行したコマンド・叩いたエンドポイント）と、確定に足りない残りの1手（誰なら実行できるか）を必ず含む。その1手が自分の権限で実行できるものなら、実行してから評決する。

評決と記載判断は別の出力である。記載判断は反証後の現在状態に対して `記載する` / `記載しない` の二値で決める。主張・根拠・具体性が、他プラットフォームのチームと発注側が読む表の行として妥当な状態にあるものを `記載する` とする。

## 成果物への反映

対象項目の評決が揃ってから書く。1つの前提崩しが他の項目の記述に波及するため、1件ずつ書かない。

`${CLAUDE_PLUGIN_ROOT}/skills/verify-items/assets/verdicts.md` の形式にならい、`<dir>/verdicts/<担当slug>.md` を Write で作る。担当した全項目に `### <番号> <評決>` の節を置く。confirmed も書く。節が無い項目は「検証していない」を意味する。

書き込みは `<dir>/verdicts/<担当slug>.md` だけ。`report.tsv`・`findings/`・`findings.md`・`issue-comment.md` は読むだけで、絶対に編集しない。反映は起動元が全担当の評決を受けてから一括で行う。

## 規律

- 項目の追加はしない。検証の過程で見つかった別の問題は完了報告に載せ、採否は起動元に委ねる
- 証拠は実行したコマンドとその出力。再現できなかった場合は、実行したコマンドと実際の出力を並べて食い違いを示す
- 推測と観測を混ぜない。「〜と考えられる」で書いたことを、後の節で事実として引かない

## 返す内容

応答は完了報告であり、記録の中身ではない。理由と経緯は verdicts ファイルにあるので、応答では繰り返さない。

```text
担当: <担当slug>
記録: verdicts/<担当slug>.md
- <番号>: <評決> / <記載する|記載しない>
無効として扱った条項: <あれば一覧。無ければ「なし」>
付随して分かったこと: <あれば箇条書き。無ければ「なし」>
```
