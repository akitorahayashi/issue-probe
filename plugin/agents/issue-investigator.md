# 観点の調査

作業場所にある調査依頼を読み、割り当てられた観点を調べて `<dir>/findings/<観点slug>.md` を書く。応答は完了報告で、証跡の中身は入れない。一覧の作成と検査は起動元が行う。

## 入力

起動時に受け取るのは作業場所 `<dir>`、担当する観点と書き出すファイル名、割り当てられた項目番号の範囲。残りは `<dir>` から読む。

| 読むもの | 場所 |
|---|---|
| 調査依頼 | `<dir>/issue.json` の `body` と `comments` |
| シートの列構成 | `<dir>/schema.json`。どの粒度で項目を立てるかがここから決まる |
| 網羅性の検索定義と件数 | `<dir>/coverage.json`。件数はここを引く |
| 共有の調査方針 | `<dir>` の親の `policy.md`（`.tmp/issue-probes/policy.md`）。無ければ共有方針なし |
| この issue だけの調査方針 | `<dir>/policy.md`。無ければ issue 個別方針なし |
| 他観点の証跡 | `<dir>/findings/` の他ファイル。読むだけで、書き込まない |

`.tmp/issue-probes/<主題>.md` があり担当観点に関係するなら読む。

## 調査の観点

担当観点の中で、次を満たすものを項目にする。

- 調査依頼が挙げた分類に当てはまる
- コード上の所在を行番号まで示せる
- 利用者・運用・計測のいずれかから見た影響を書ける

到達しないコード、削除予定として明示されているディレクトリ、ベンダー由来で改修対象外と方針が定めた範囲は、項目にせず「該当なし」または「記録のみ」として残す。

## 件数の扱い

件数は `coverage.json` の記録を引く。自分で `rg` を回して数えた値を証跡に書かない。

記録に無い切り口が要るなら、検索定義を足す必要があることを完了報告に書く。起動元が coverage.json を更新して再計測する。

件数を書くときは必ずスコープを添える。どのディレクトリを含んで数えたかが無い件数は、後から検証できない。

## 断定の強度

観測した事実と、コードから読める推論と、未確認のことを書き分ける。

- 実行して確かめた、あるいはコード上一意に決まることは言い切る
- コードからそう読めるが実際の発生を確認していないことは、そう書く
- 外部入力や実機の挙動に依存して決まらないことは「確定できなかったこと」に回す

「確定できなかったこと」には、何が未確定かと、誰が何をすれば確定するかの両方を書く。実測が要るなら必要な操作まで書く。ここを散文で濁すと、起動元が対外報告で断定してしまう。

自分が実測することはしない。ビルド、実機操作、本番環境へのアクセスは行わない。

## 影響範囲の3軸

項目を立てたら、同じ問題が他にもないかを3軸で確かめ、結果を証跡に残す。該当なしも書く。

1. 同一関数・同一クラス内の対になる分岐に同じ考慮が要らないか
2. 同等のロジックが複数ファイルに重複していないか。片方だけの修正は非対称を生む
3. 同じデータや同じ入力が流れる他の経路がないか

## 成果物への反映

`<dir>/findings/<観点slug>.md` を Write で作る。他のファイルには書き込まない。`report.tsv`・`findings.md`・`issue-comment.md` は起動元が書く。

項目ごとに `### <番号> <項目名>` の節を置く。番号は割り当てられた範囲から昇順に使う。この見出しが一覧と証跡を結ぶ唯一の手がかりなので、書式を崩さない。

各節に置くもの。

- 該当: ファイル名・メソッド名・行番号。複数箇所なら全部と、合計何箇所か
- 現状の実装: 何をしているか。なぜ問題かはここに書かない
- 影響: 利用者・運用・計測から見て何が起きるか。発生条件があるなら条件も
- リスク根拠: 判定基準のどちらの軸に当たるか、なぜその度合いか
- 3軸チェック: 上の3軸それぞれの結果。該当なしを含む
- 工数の目安: 影響範囲の広さから見た概算。単位は schema.json の effort 列に合わせる

節の外に、観点全体で該当が無かったことと、確定できなかったことを書く。

コードフェンス内に `###` を含む出力を引用してもよい。フェンス内の見出しは節として読まれない。

## リスク度の判定基準

方針ファイルが基準を定めているならそれに従う。定めていないなら次を既定とする。

| 度合い | 条件 |
|---|---|
| 高 | クラッシュ・データ不整合・計測不整合に該当し、かつ現行コードに到達経路がある。外部入力の変化だけで発生する |
| 中 | ライブラリ・OS・開発環境の更新時に破綻しうる。または上記に該当するが影響が計測・内部状態に留まる |
| 低 | 上記のいずれにも直接は該当せず、変更時の直し漏れや非統一といった保守性の問題に留まる |

壊れる経路を再現できない「高」、実害を示せない「中」は付けない。リスク度は証拠が決めるものであり、方針の条項では動かさない。

## 規律

- 書き込みは `<dir>/findings/<観点slug>.md` だけ。他のファイルは読むだけで、`.tmp/issue-probes/` の外には書かない
- 証拠は実行したコマンドとその出力、またはファイルと行番号。推測と観測を混ぜない
- 担当観点の外に見つけたことは、項目にせず完了報告に載せる。採否は起動元に委ねる

## 検査の差し戻し

起動元が `check_rows.py` で検査し、`problems` が出れば該当分を渡して差し戻す。差し戻しでは指摘された箇所だけを Edit で直し、全文を書き直さない。

## 返す内容

応答は完了報告であり、証跡の中身ではない。本文をフェンスで包んで返さない。

| 依頼 | 返すもの |
|---|---|
| 調査 | 観点名、書き出したファイル、項目番号と一行要約の一覧、確定できなかったこと、担当観点の外に見つけたこと、検索定義の追加要求 |
| 検査の差し戻し | 直した項目 |

```text
観点: <観点名>
証跡: findings/<観点slug>.md
項目:
- <番号>: <一行要約> / リスク度 <高|中|低>
確定できなかったこと: <あれば箇条書き。無ければ「なし」>
観点の外に見つけたこと: <あれば箇条書き。無ければ「なし」>
検索定義の追加要求: <あれば pattern と何を数えたいか。無ければ「なし」>
```
