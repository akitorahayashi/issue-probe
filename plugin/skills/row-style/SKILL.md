# 一覧セルの文体

項目のフィールドは export-items がそのままシートのセルにする。シートは他プラットフォームの開発チームと発注側が同じ表で読み、読み手はこのコードベースを知らない。`#### 根拠` はシートに出ないので、この文体が要るのはフィールドだけである。

## 貼り付けを壊さない

値に改行・タブ・復帰を入れない。シートは改行で行、タブで列を切るため、値の中の1文字が表全体をずらす。

長い内容は自分で1行に畳まない。コロンの後を空にしてネストした箇条で書き、`1. … 2. …` への畳み込みは export-items に任せる。畳んだ形を手で書くと、書いている間も後から読むときも追えなくなる。

コードフェンスや Markdown の記法を使わない。シートはそれを装飾として解釈しない。

書くことが無い欄は「なし」と書く。空のままにすると、書き忘れと区別が付かない。

## 読み手に合わせる

識別子を並べない。何が起きるかを先に書き、識別子は場所を示すためだけに添える。

```text
悪い: LGCObject.valueForKey が NSNull を nil へ正規化するため as! String が失敗する
良い: APIがidをnullや欠落で返すと番組表表示時に即クラッシュする
```

専門用語を使うときは、その行の中で意味が取れるようにする。「スウィズル」ではなく「実行時にSDKのメソッドを差し替えている」と書く。

## 事実と推測を書き分ける

確認できたことは言い切る。「〜している」「〜になる」。

コード上そうなると読めるが実際の発生を確認していないことは、そう書く。「〜と考えられる」「〜しうる」。

確認していないことは「未確認」と明示する。確認できない理由と、確認する手段があれば添える。

過去に起きた事象と、これから起きうる事象を混ぜない。実績があるものは「実績あり」と書き、無いものに実績があるかのような書き方をしない。

## フィールドごとの書き方

該当箇所は、ファイル名・メソッド名・行番号で書く。複数箇所は「L318,329,355」のように並べ、全部で何箇所かを添える。

現状は、何をしているかを書く。なぜ問題かは書かない（それは想定される事象が持つ）。

想定される事象は、利用者や運用から見て何が起きるかを書く。内部状態の説明で終わらせない。

影響範囲は、ネストした箇条で1件1行にし、「ファイル名 該当機能（行） → 何をするか」の形で書く。変更しないが確認するファイルも「→ 変更なし・○○を確認する」の形で同じ箇条に並べる。読み手が改修の全体量を把握できることが目的である。

工数は「Nh（設計: Xh/ 実装: Yh）」の形で、合計を先頭に置く。合計を先頭に置くのは、それが機械的に合算されるためである。内訳の根拠が要る項目は「※」で1文添える。工数に何を含め何を含めないかは、findings.md の前置きで一度宣言する。

備考は、本文に書くと結論がぼやけるが読み手が知るべきことを置く。実測で分かったこと、他プラットフォームの記入例との関係、別課題として切り出したものなど。

## 粒度

1事象1項目にする。grep のヒット単位で項目を作らない。同じ原因で同じ直し方になるものは1項目にまとめ、件数を該当箇所に書く。

同じ表に他プラットフォームの記入例があるときは、その粒度と書式に合わせる。表は横断で比較されるため、自分の行だけ粒度が違うと比較できない。

## 部分的に直すとき

一部の項目だけを直したあとに、全項目で語尾と敬体、断定の強度、フィールドごとの書式が揃っているかを見る。1項目だけ文体が違うと、その項目の信頼度が下がって見える。
