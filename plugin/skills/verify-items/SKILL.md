# 項目の再検証

`.tmp/issue-probes/<番号>/` にある一覧の項目を、証拠の再現と前提への反証で疑い直す。関連する複数 issue の検証は並行する。

一覧は同じ調査の流れの中で作られており、同じ推論経路で確認しても独立性がない。シートに貼れば他プラットフォームのチームと発注側が読むため、根拠の弱い断定が外に出る前に崩しにいく。

item-verifier が担当項目の反証と `verdicts/<担当>.md`、メインがユーザーとの対話、評決の統合、成果物への反映を担当する。

以下の `<plugin-root>` は、この SKILL.md の2階層上として解決する。成果物の正本と編集責任は[調査成果物の扱い](../probe-workspace/SKILL.md)に従う。

## 更新するファイル

| 更新先 | 内容 |
|---|---|
| `<dir>/verdicts.md` | メインが[verdicts](assets/verdicts.md)の形式で1ラウンドを追記する |
| `<dir>/report.tsv` | メインが評決後の状態へ直す |
| `<dir>/findings/<観点>.md` | メインが評決後の状態へ直す |
| `<dir>/issue-comment.md` | メインが評決後の要約・改修計画・関係者確認事項へ直す |

## 手順

### 1. 対象の確定

依頼文から issue の番号を取る。受け取れなければ質問し、回答を得てから進める。

issue 番号ごとに実行する。

```bash
python3 <plugin-root>/scripts/check_rows.py <dir>
```

- 終了コード0: 現在の一覧は整合している。全項目を検証対象にする
- 終了コード1: `problems` を先に解消する。整合していない一覧を反証しても、崩れているのが主張なのか記述なのか切り分けられない
- 終了コード2: 成果物が読めない。`action` に従って直してから再実行する

`info` に「件数の計測時のコミットが調査時点と違います」が出た場合は、`count_hits.py` を再実行してから進む。古い件数を根拠に反証しても結論が出ない。

依頼文が項目を名指ししていればそれを、していなければ全項目を対象にする。

### 2. 検証

対象を担当に分ける。項目数ではなく反証の型で分ける。「本当に壊れるのか」「本当に経路が繋がっているか」「本当に乖離しているか」のように、崩し方が同じものをまとめる。

全担当の `issue-probe:item-verifier` を1つのメッセージで並列起動する。Agent ツールの `subagent_type` は `issue-probe:item-verifier`。各 prompt に書くのは次だけで、項目の内容は verifier が `<dir>` から読む。

- 作業場所 `<dir>`
- 担当する項目番号と、書き出すファイル名 `verdicts/<担当slug>.md`
- 崩してほしい前提（メインが特に根拠が弱いと判断しているもの）
- 本番環境・認証付きアクセスの許可（依頼文にあるときだけ。無ければ書かない）

崩してほしい前提は具体的に書く。「本当か確かめて」ではなく、「この主張は◯◯を仮定しているが、それは確認されていない」の形で渡す。ここが反証の質を決める。

verifier は評決と記載判断を返す。全担当の応答とエージェントIDを受け取ってから手順3へ進む。

### 3. 統合と反映

全評決が揃ってから反映する。1つの前提崩しが他の項目の記述に波及するため、1件ずつ反映しない。

`verdicts/<担当>.md` を `<dir>/verdicts.md` に1ラウンドとして統合する。`## <codeSha>` の見出しで開き、担当ごとの節を並べる。既にファイルがあるときは末尾に足し、過去のラウンドは書き換えない。統合後、分割ファイルは削除する。

評決を成果物へ反映する。

- confirmed: 何もしない
- revise: report.tsv の該当セルと `findings/` の該当節のうち、ずれている箇所を直す。リスク度が変わったら enum 列も直す
- delete: report.tsv の行を削除し、`findings/` の節は残す。番号は詰め直さず欠番にする。理由は verdicts.md にのみ残る
- unresolved: 項目は残し、`findings.md` の「確定できなかったこと」に、試したことと確定に必要な1手を書く

リスク度が動いたら issue-comment.md の要点と改修計画の段階分けも直す。件数が変わったら coverage.json の記録と突き合わせる。

### 4. 受け入れ

```bash
python3 <plugin-root>/scripts/check_rows.py <dir>
```

終了コード0まで直す。delete した項目が `findings/` に残っているのに verdicts.md へ評決を書き忘れると、ここで problem になる。

### 5. 報告

issue 番号ごとに次を伝える。

- 項目番号ごとの評決と記載判断の一覧
- リスク度や件数が動いた項目と、その理由の要約
- delete した項目と、その根拠
- unresolved の項目と、確定に必要な1手
- verifier が担当外に見つけたことの一覧
- 更新後の工数合計とリスク分布

## 規律

- 対象リポジトリへの書き込みは `.tmp/issue-probes/` 配下に置く
- verifier は項目を追加しない。見つかった別の問題は報告し、採否はユーザーが決める
- 評決と記載判断は別の軸である。主張が成立していても、対外シートに出す記述として不足なら記載判断は `記載しない` になる
- リスク度は証拠が決める。方針の条項を根拠に動かさない
