# 項目の再検証

`.tmp/issue-probes/<番号>/findings.md` の項目を、証拠の再現と前提への反証で疑い直す。関連する複数 issue の検証は並行する。

一覧は同じ調査の流れの中で作られており、同じ推論経路で確認しても独立性がない。シートに貼れば他プラットフォームのチームと発注側が読むため、根拠の弱い断定が外に出る前に崩しにいく。

担当項目の反証と評決の報告はitem-verifier担当、ユーザーとの対話、評決の記録、成果物への反映はメインが担当する。サブエージェント委譲を利用できる場合は担当を並列起動して識別子を保持し、利用できない場合はメインが同じ責務を順次実行する。成果物はメインだけが書く。

成果物の正本と編集責任は[調査成果物の扱い](../probe-workspace/SKILL.md)に従う。

## 更新するファイル

| 更新先 | 内容 |
|---|---|
| `<dir>/verdicts.md` | メインが[verdicts](assets/verdicts.md)の形式で1ラウンドを追記する |
| `<dir>/findings.md` | メインが評決後の状態へ直す |
| `<dir>/issue-comment.md` | メインが評決後の要約・改修計画・関係者確認事項へ直す |

## 手順

### 1. 対象の確定

依頼文から issue の番号を取る。受け取れなければ質問し、回答を得てから進める。

issue 番号ごとに実行する。

[check_items.py](../../scripts/check_items.py)をPython 3で実行し、`<dir>`を渡す。

- 終了コード0: 現在の一覧は整合している。全項目を検証対象にする
- 終了コード1: `problems` を先に解消する。整合していない一覧を反証しても、崩れているのが主張なのか記述なのか切り分けられない
- 終了コード2: findings.md が読めない。`action` に従って直してから再実行する

`info` に「件数の計測時のコミットが調査時点と違います」が出た場合は、`count_hits.py` を再実行してから進む。古い件数を根拠に反証しても結論が出ない。

依頼文が項目を名指ししていればそれを、していなければ全項目を対象にする。

### 2. 検証

対象を担当に分ける。項目数ではなく反証の型で分ける。「本当に壊れるのか」「本当に経路が繋がっているか」「本当に乖離しているか」のように、崩し方が同じものをまとめる。上限は5体。

[item-verifierの責務](../../agents/item-verifier.md)を持つ担当を割り当てる。各担当へ渡すのは次だけで、項目の内容は`<dir>`から読む。

- 作業場所 `<dir>`
- 担当する項目番号
- 崩してほしい前提（メインが特に根拠が弱いと判断しているもの）
- 本番環境・認証付きアクセスの許可（依頼文にあるときだけ。無ければ書かない）

崩してほしい前提は具体的に書く。「本当か確かめて」ではなく、「この主張は◯◯を仮定しているが、それは確認されていない」の形で渡す。ここが反証の質を決める。

各担当は項目ごとの評決の節と記載判断を返す。全担当の結果を揃えてから手順3へ進む。

### 3. 記録と反映

全評決が揃ってから反映する。1つの前提崩しが他の項目の記述に波及するため、1件ずつ反映しない。

返された節を `<dir>/verdicts.md` に1ラウンドとして書く。`## <現在のコミット>` の見出しで開き、担当ごとの節を番号順に並べる。既にファイルがあるときは末尾に足し、過去のラウンドは書き換えない。

評決を findings.md へ反映する。

- confirmed: 何もしない
- revise: 該当節のうち、ずれているフィールドと `#### 根拠` を直す。リスク度が変わったら見出しの `[ ]` も直す
- delete: 該当節を削除する。番号は詰め直さず欠番にする。主張と落とした理由は verdicts.md の delete 評決にのみ残る
- unresolved: 項目は残し、「確定できなかったこと」に、試したことと確定に必要な1手を書く

リスク度が動いたら issue-comment.md の要点と改修計画の段階分けも直す。件数が変わったら coverage.json の記録と突き合わせる。

### 4. 受け入れ

[check_items.py](../../scripts/check_items.py)をPython 3で実行し、`<dir>`を渡す。

終了コード0まで直す。delete した項目の delete 評決を書き忘れると、その番号が「主張の残らない欠番」としてここで problem になる。

### 5. 報告

issue 番号ごとに次を伝える。

- 項目番号ごとの評決と記載判断の一覧
- リスク度や件数が動いた項目と、その理由の要約
- delete した項目と、その根拠
- unresolved の項目と、確定に必要な1手
- verifier が担当外に見つけたことの一覧
- 更新後の工数合計とリスク分布

シートへ貼る形が要る場合は `export-items <番号>` を示す。paste.tsv は再検証後の findings.md から作り直す。

## 規律

- 対象リポジトリへの書き込みは `.tmp/issue-probes/` 配下に置く
- verifier は項目を追加しない。見つかった別の問題は報告し、採否はユーザーが決める
- 評決と記載判断は別の軸である。主張が成立していても、対外シートに出す記述として不足なら記載判断は `記載しない` になる
